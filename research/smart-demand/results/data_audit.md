# 智能分仓数据审查

实际读取完整 SQLite：商品日记录 232,621 行、32 列，1,000 个商品；日期 2014-10-01—2015-12-27，453 个日期。商品—日期无重复，所有数值字段均已检查缺失、非有限值、负数和分位数，详见 `field_profile.csv`。

预测目标选 `qty_alipay`（成交件数），是已记录支付成交量，不等于未满足需求。总量 1,955,102 件；明确记录为零的行占 51.89%。`qty_gmv` 是另一下单口径，83,791 行与成交件数不同，不能混作同一答案。

只有 99 个商品覆盖全期。单品记录数中位 206.5 天；628 个商品在首末记录之间有缺日，共 22,855 个商品日。缺记录不代表销量为零，商品首次出现前和最后出现后的记录也未知。逐商品和逐日范围保存在 `item_coverage.csv`、`date_coverage.csv`。

类目、大类、品牌、供应商在同一商品内均未发现变化。编号应按类别处理，不能把编号差当业务距离。未来浏览、加购、收藏、下单、成交和金额都属于未来实际发生结果；预测只能用截止日及以前的记录。同期 `num_alipay` 与目标相关性很高，直接使用会把结果信息带入输入。

成交与下单的日期口径可能不同：成交件数大于当日下单件数的行数是 3228。另有 18308 行成交件数为零、成交金额却大于零。现有说明不能解释金额与件数的不一致；保留原成交件数目标，不按金额反推数量、不单凭不相等删除记录。其他数量、人数和金额核对见 JSON 的 consistency_check_counts_not_proven_errors。

购物节尖峰会影响总量误差，因此实验要同时报告普通窗口与含固定购物节日期的窗口；这些分组只用于检查误差，不能用后来已知的高峰决定模型。全国汇总反映当前记录商品集合，商品覆盖随日期变化，不能称为全区域完整需求。

`Cost` 为 1,000 个商品在 `all`、1—5 六个仓口径上的 6,000 行成本，商品键全部可连接且商品—仓键不重复。商品行为表没有区域或仓字段，因此成本表不能补出区域销量、区域偏好或各仓历史需求。

SQLite 中文元数据可正常读取，未发现 Unicode 替换字符；旁边的元数据 CSV 需按 GB18030 读取。终端编码不匹配会显示乱码，不能把显示问题当作源数据损坏。所有字段概况、元数据和来源 SHA256 在 `data_audit.json`。

本次采用只读 SQLite 连接，运行前后 SHA256 相同。脚本还用独立 SQL 聚合逐一核对导出的 1,000 行商品表和 453 行日期表，核对缺日数、最大间隔和目标总量；结果见 `data_audit_validation.json`。复跑：

```powershell
.\.venv\Scripts\python.exe research/smart-demand/audit.py
```

建议模型先比较同一十四日目标上的近期中位数、近期均值、星期基线和共享小网络。任何标签缺日都应记录评估覆盖，不能用插值后的答案证明模型更准。
