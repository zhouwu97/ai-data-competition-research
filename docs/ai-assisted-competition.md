# AI辅助参赛：怎样让它的输出可以检查

这份流程面向大量依靠AI写代码、选方法和写报告的人。AI可以帮你推进工作，你仍需要知道任务、输入、比较对象与结论依据。未知词先查[新手术语](beginner/glossary.md)。

## 1. 先保存分析，再读新方案

先只给本次赛题正文和已经确认的数据字典，要求至少两条路线，说明必要假设、最小实现、评价与反例。记录时间、已提供材料、未知项和采用条件，再阅读新的他人方案。

~~~text
先解释赛题要求和每种数据的作用，陌生术语用例子说明。
给两条可行路线，分别写：成立条件、最小输出、检查方法、成本、失败证据。
不要按技术新颖或文章长度选题；缺少数据或评分就明确待确认。
~~~

已经读过获奖方案的分析属于参考后的判断。新建聊天不保证模型没有先验知识；本流程保存的是本次材料暴露和判断顺序，不保证严格实验意义的盲测。

## 2. 代码输出必须对应执行记录

让AI先建立简单基线与输入检查，再只做一项改动。保存输入版本、源码摘要、命令、依赖、日志、退出状态、结果和失败。

~~~text
逐段说明这段代码读什么、改变什么、输出到哪里。
先运行基线，再在同一评价条件下做一个改动。
结论必须引用实际结果文件；没运行写“计划”，报错写“失败”。
不要删除数据检查来制造成功，也不要编造提升百分比。
~~~

教学示范的[实际运行记录](../examples/results/run_manifest.json)与[日志](../examples/results/run.log)可作为格式参考。合成数据、真实数据、作者自述与我们实测必须分别标注。

## 3. 做一次只找反例的审核

可以在同一项目安排独立审查阶段：冻结结果，让审核只检查任务遗漏、泄漏、公式、比较不公平、版本不一致和结论越界。另一个AI同意不等于验证，审核仍须指出具体输入、代码和结果。

~~~text
先不要给改进建议，找出这个结论最可能不成立的条件。
核对任务是否遗漏、特征当时是否可用、指标与比较是否一致。
对每项问题写证据、严重性、复查方法；证据不足的怀疑标为待验证。
~~~

代码检查只能覆盖设计好的情形。[错误示范](../examples/failure_cases.py)不会保证发现所有OOF污染或业务口径问题。

## 4. 报告数字逐项追溯

重要结论列“结论—指标定义—输入版本—结果文件—计算位置—限制”。图表、正文和答辩使用同一版本。模拟效率与实测效率分开，算法分组与真实价值分开。

~~~text
审查报告每个重要数字和因果结论，指出对应结果文件和计算过程。
没有支持证据的结论改为假设或待验证，不补写虚构实验。
核对当届AI、外部数据、开源代码、模型/API使用与引用要求。
~~~

[validate_research.py](../scripts/validate_research.py)检查四项教学数值与文件摘要，不自动审核所有报告句子、创新或获奖可能性。正式成果仍需按[规则清单](../competition-requirements/README.md)审阅。

## 5. 新手怎样判断自己是否真的理解？

你能解释一行代表谁，每个主要特征来自哪里，为什么选这种检查方式，简单方法是什么，哪些结果会推翻判断。说不清时让AI举更小的例子，再用手算或实际输出核对。
