# 参赛工作方法

以下是本仓库整理的实践建议。技术依据见末尾官方文档，具体比赛限制仍看赛规。

## 1. 把赛题改写成可计算的问题

写清一条数据代表谁、预测什么、什么时候预测、当时能拿到哪些字段、如何计算分数。客户流失预测不能使用客户流失后才产生的字段；需求预测不能用未来订单。

先建立数据字典：字段单位、缺失含义、主键、时间范围、目标、可用时点。再做缺失率、重复率、类别分布和时间覆盖检查。保存清洗前后的行数与排除原因。

## 2. 先确定验证方式

| 数据关系 | 建议考虑的切分 |
| --- | --- |
| 近似独立的分类样本 | 分层切分；检查重复样本 |
| 同一用户或设备多条记录 | 按主体分组，避免同一主体出现在两侧 |
| 预测未来 | 按时间向后切分，模拟实际预测窗口 |
| 多仓库 / 多区域 | 对齐未来测试场景，必要时同时检查时间和主体泛化 |

填补、标准化和特征选择在训练部分拟合，再应用到验证部分；用 Pipeline 组织。建好验证以后不要为了迎合榜单反复更换它。验证分数只是性能估计，不能当作真实业务收益。

## 3. 建一个够简单的 baseline

分类先比较多数类 / Dummy 与简单模型；回归先比较常数预测与线性或树模型；时间预测先比较季节和近期均值；文本先比较 TF-IDF 分类与预训练模型。目的在于知道复杂方法增加了多少价值。

一次实验只回答一个问题：新增时间特征是否有用、某种缺失处理是否稳定、换模型是否值得耗时。固定切分，记录指标方向、种子、运行环境和 Git 版本。波动明显时检查多个切分或种子，而不是只汇报最好的一次。

## 4. 读开源方案时看六件事

数据口径；验证设计；真正有效的特征；模型及耗时；融合输入是否为 OOF（折外预测）；提交生成流程。区分训练、验证、测试与赛后改进。遇到旧框架先摘方法，不急着升级整套环境。

## 5. 把结果写成可检查的报告

每张核心图回答一个问题，并标数据范围、单位和样本数。结论指出证据所在；建议说明适用对象、成本和判断条件。成本、路程、效率等估计明确假设，实际测试与模拟分开写。

答辩能解释：数据为什么可信，验证为什么合理，baseline是什么，改进有什么证据，失败在哪，业务怎么用。保留一个能从数据输入走到结果输出的最小演示。

## 6. 让 AI 帮到可核查的地方

适合交给 AI：解释字段、写清洗草稿、排查报错、提出实验假设、改报告表达。交付后自己检查数据关系、指标、切分和实际日志。要求 AI 引用真实文件与运行结果；没跑的实验只能写成计划。

可用任务描述：

> 先读赛规和数据字典，列目标、指标、可用字段和潜在泄漏。提出一个简单基线与验证方案，每个实验记录命令、版本、耗时和结果。报告只写已有证据，待做事项单列。
